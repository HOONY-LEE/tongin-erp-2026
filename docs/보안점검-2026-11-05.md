# 통인 ERP 보안 점검 보고서 (2026-11-05)

고객정보(이름·전화·주소·접수/A/S 이력)가 새어 나갈 수 있는 길을 중심으로 서비스 전체를 점검했다. 막을 수 있는 것은 `fix/security-hardening` 브랜치에서 고쳤다. 동작이 바뀌어 결정이 필요한 것은 고치지 않고 [결정이 필요한 것](#결정이-필요한-것)에 선택지로 적었다.

- 범위: `apps/api`(NestJS·Prisma), `apps/web`(React), `packages/shared`, `desktop`(Electron), 배포 설정(`render.yaml`·`vercel.json`·Dockerfile), 의존성.
- 방법:
  - 코드 읽기: 컨트롤러 59개·라우트 445개.
  - 실제 API 호출: 로컬 DB 시드 데이터로 했다.
    - 지점장 계정 `ilwoo_nam`(잠실A점, 데이터범위 ORG)으로, 파라미터 없는 GET 116개를 모두 불렀다. 응답에 다른 지점 고객 전화번호 97개가 들어 있는지 찾았다.
    - id를 받는 GET 70개에는 다른 지점 고객·접수·견적·계약·작업·주문·A/S·입금 id를 넣어 불렀다.
    - 쓰기 라우트는 빈 값으로 하나씩 불렀다.
  - 고친 뒤 같은 검사를 다시 돌렸다. 다른 지점 데이터 노출 0건, 5xx 0건이었다. 시험 중 만든 행은 지웠다.
- 표의 "확인" 칸: **재현** = 실제 API 호출로 확인. **코드** = 코드 경로로 확인.

## 치명

### C1. 작업일정 iCal 내보내기에 데이터 범위가 없음 — 수정 (재현)

- **경로**: `GET /api/calendar/work-orders.ics`(`WORK_ORDER.READ`). 이 권한은 가맹점·전속업체·현장팀 기본 권한이다.
- **문제**: `calendar.service.ts`의 `workOrdersIcs()`가 사용자를 받지 않는다. 그래서 전 지점 작업을 최대 1000건까지 돌려준다. 각 일정에는 고객 이름, 출발지 주소(동·호수까지), 도착지 주소가 들어 있다.
- **재현**: 지점장 `ilwoo_nam`으로 호출했더니 40건이 나왔다. 회사 전체이고, 다른 지점 고객의 이름과 주소가 들어 있었다.
- **고친 내용**: 작업오더 목록과 같은 범위만 돌려준다. 전속업체는 자기 업체 작업만, 그 밖에는 데이터범위 조직만이다. 고객은 이름만 읽는다. 고친 뒤 같은 계정으로 1건(자기 지점)만 나온다.

## 높음

### H1. 접수 등록 때 전화번호로 다른 지점 고객이 연결되어 이름·이력이 드러남 — 수정 (재현)

- **경로**: `POST /api/leads`, `PATCH /api/leads/:id`(가맹점 기본 권한), `GET /api/leads/:id/case`
- **문제**:
  - 같은 번호의 고객을 찾는 SQL(`findCustomerByPhone`)이 범위 없이 전체 고객을 뒤진다.
  - 본문의 `customerId`도 확인하지 않는다.
  - 케이스 화면은 그 고객의 A/S 이력을 모든 지점에서 모아 보여 준다.
- **재현**: 지점장이 고객명 "아무개"에 다른 지점 고객의 번호를 넣어 접수했다. 응답의 고객 이름이 그 번호의 실제 주인 "황수아"로 나왔다. 아무 번호나 넣어 주인 이름을 알아낼 수 있었고, 그 고객을 내 지점 접수에 붙여 캠페인 대상으로 끌어올 수도 있었다.
- **고친 내용**:
  - `ScopeService.assertCustomer`를 추가했다.
  - 번호로 찾을 때는 내 범위와 담당 지점이 없는 고객 안에서만 찾는다. 범위 밖에 같은 번호가 있어도 알려 주지 않고 내 지점 고객을 새로 만든다.
  - 고른 `customerId`는 범위를 확인한다.
  - 케이스 화면의 A/S 이력은 내 범위 지점이 받은 것만 보여 준다.

### H2. 계약 조회 응답에 토스 웹훅 비밀값이 실려 지점이 '입금 완료'를 꾸밀 수 있음 — 수정 (재현: 필드 노출)

- **경로**:
  - `GET /api/contracts/:id`, `GET /api/contracts/:id/payments`: `payments`의 `pgRef`·`pgSecret`이 응답에 그대로 나간다.
  - `POST /api/public/payments/toss/webhook`: 이 둘만 맞으면 결제를 PAID로 바꾼다.
- **문제**: 가맹점은 일부러 `PAYMENT.UPDATE`를 받지 않는다. 그런데 이 값을 읽어 직접 웹훅을 부르면 입금 확인과 접수 계약 전환을 할 수 있었다. 토스 키를 쓰는 운영에서 생기는 문제다.
- **같은 문제로 함께 막은 값**:
  - 계약의 `signToken`: 고객 서명 링크. 알면 고객 대신 서명할 수 있다.
  - 계약의 `signatureImage`: 고객 서명 그림.
- **고친 내용**:
  - `PrismaService`에서 이 세 열을 기본으로 읽지 않는다(Prisma 전역 `omit`).
  - 꼭 필요한 곳(웹훅 검증, 견적서 보내기 때 링크 만들기)만 `omit: { 열: false }`로 다시 읽는다.
  - 견적서 문서의 서명 그림은 원래 `select`로 고른 것이라 그대로 나온다.
  - 세 가지 모두 실제 DB로 확인했다.

### H3. 캘린더 '조직 보기'에서 다른 조직을 고르면 범위가 무시됨 — 수정 (재현)

- **경로**: `GET /api/calendar/events?scope=ORG&orgUnitId=<다른 지점·본사 부서>`(`CALENDAR.READ`, 가맹점 기본 권한)
- **문제**: 자체 일정에는 범위 검사가 있었지만, 작업 일정과 승인된 휴가 쪽은 `orgUnitId`를 그대로 썼다. 그래서 다른 지점 고객 이름·이동 경로와 본사 직원 휴가 종류·사유가 보였다.
- **고친 내용**: 세 군데 모두 같은 범위 필터(`orgFilter`)를 쓴다. 고친 뒤 다른 지점을 고르면 빈 목록이 나온다.

### H4. 결재선을 비워 보내면 휴가·근태 정정이 바로 승인됨 — 수정 (재현)

- **경로**: `POST /api/leave/requests`, `POST /api/attendance/fix-requests`. 본문 `line: []`, 본인만 넣은 결재선, 참조만 넣은 결재선 모두 해당한다.
- **문제**: 결재할 사람이 남지 않으면 '자동 승인'으로 처리해 자기 휴가와 출퇴근 기록을 스스로 확정할 수 있었다.
- **고친 내용**: 신청자가 고친 결재선에 본인 말고 결재자가 없으면, 기본 결재선에 결재자가 있을 때 400으로 막는다. 대표처럼 위에 아무도 없어 기본 결재선이 비는 경우는 예전처럼 바로 승인된다.
- **남은 것**: 친한 동료 한 명만 결재자로 넣는 것은 여전히 된다. 결재선을 어디까지 고치게 둘지는 결정이 필요하다([D7](#d7-결재선을-어디까지-고치게-둘지)).

### H5. 지점 직원이 회사·그룹 드라이브의 편집자 — 본사 파일을 지우고 휴지통까지 비울 수 있음 — 수정 (재현)

- **경로**:
  - `GET /api/drive/spaces`
  - `DELETE /api/drive/items/:id`
  - `DELETE /api/drive/trash`
- **문제**: 드라이브 권한이 내 조직의 **상위 조직 전부**에 편집자(EDITOR)를 줬다. 지점은 통인익스프레스(COMPANY) 아래, 그 위는 통인그룹(GROUP)이다. 그래서 지점장 100여 명이 회사·그룹 드라이브를 읽고 지우고 영구 삭제할 수 있었다.
- **고친 내용**: 위로 올라가다 지점(BRANCH)을 지난 뒤의 조직 드라이브는 보기(VIEWER)만 준다.
  - 고친 뒤 지점장: 자기 지점 = EDITOR, 회사·그룹 = VIEWER
  - 본사 마케팅 직원: 마케팅·회사·그룹 모두 EDITOR(그대로)

### H6. 공유 에이전트를 만든 사람이 다른 사람이 돌린 실행 결과를 그대로 봄 — 수정 (코드)

- **경로**: `GET /api/agent-blueprints/:id/runs`(AI.MANAGE)
- **문제**: 에이전트는 실행한 사람의 권한과 범위로 돈다. 그런데 만든 사람이 실행 기록의 입력·결과·단계 기록을 모두 받았다. 예를 들어 "고객 검색 → 결과 출력" 에이전트를 공개해 두면, 관리자가 실행했을 때 관리자 범위의 고객 명단이 만든 사람에게 넘어갔다.
- **고친 내용**: 남이 돌린 실행은 상태와 시간만 준다. 입력·결과·오류·단계 기록은 빼고 `hidden: true`를 붙인다. 슈퍼관리자는 예외다.

### H7. 공유 에이전트의 '승인' 노드로 쓰기 도구를 몰래 실행시킬 수 있음 — 수정 (코드)

- **문제 1**: 승인 노드는 만든 사람이 쓴 문구만 보여 준다. 승인하면 바로 다음 쓰기 도구가 실행자 권한으로 실행된다. 예를 들어 "주간 보고서를 저장할까요?" 뒤에 '내 계정에 관리자 그룹 주기'를 숨겨 둔 에이전트를 관리자가 실행해 승인하면, 만든 사람이 관리자 권한을 얻는다.
- **문제 2**: `erp_estimates_send`(견적서 보내기, 고객에게 문자가 나감)가 '문자는 매번 승인' 대상에서 빠져 있었다.
- **고친 내용**:
  - 만든 사람이 아닌 사람이 돌리면, 승인 노드를 지났어도 쓰기 도구마다 실제 도구·인자·미리보기를 보여 주고 다시 승인받는다(`RunState.ownBlueprint`). 예전에 저장된 실행도 같다.
  - 견적서 보내기도 매번 승인 대상에 넣었다.

**M3에서 막은 네 가지**:

1. 내 계정을 다른 직원(예: 대표)에 다시 이어 그 사람의 결재·인사 화면을 여는 것: 본인 계정의 연결 직원은 바꿀 수 없게 했다. 이미 다른 계정과 이어진 직원은 고를 수 없다. 계정을 새로 만들 때도 같다.
2. 범위 밖 계정을 고치거나, 소속을 내 범위로 끌어와 권한을 바꾸는 우회: 직원 연결·직원 정보·활성 전환에도 권한 그룹 바꾸기와 같은 기준을 적용했다. 범위 밖 조직과 전체관리자 계정은 손댈 수 없다.
3. 퇴사자 계정을 다시 켜는 것: 퇴사·비활성 직원의 계정은 켤 수 없다.
4. 직원을 '비활성'으로 바꿔도 로그인이 살아 있던 것: 직원을 비활성으로 바꾸면 계정도 끈다.

**M8에서 고친 것**:

- 서버 `/api/health`가 `demo`를 알려 준다. `DEMO_SEED=off`이면 `false`다.
- 로그인 화면은 `demo`가 `true`일 때만 데모 계정 목록을 보여 준다. 실운영으로 바꾸면 저절로 사라진다. 지금 시연 서버는 그대로다.
- 공개된 기본 비밀번호(`admin1234`·`tongin1234!`)로는 비밀번호를 바꾸거나 계정을 만들 수 없다.

**M15 의존성 정리**:

- pnpm `overrides`로 올린 것: proxy-addr(IP 위조, 치명), body-parser, qs, multer, brace-expansion, react-router
- 직접 올린 것: jspdf 2.5.2 → 4.2.1(치명, 안에 든 dompurify XSS 포함). 쓰는 API는 addImage·addPage·save뿐이라 호환된다. 웹 빌드는 통과했다.

## 결정이 필요한 것

### D1. 화면에서 전화번호·주소 가리기

지금은 목록·상세 모두 전화번호와 상세 주소(동·호수)가 그대로 보인다. 표 내보내기(CSV·엑셀)는 화면에 보이는 것을 그대로 받는다.

- A. 목록에서는 `010-****-1234`, 주소는 시·구까지만. 상세 화면에서 '보기'를 누르면 보이고, 누른 것을 기록한다. (권장)
- B. 권한(`CUSTOMER.PII`)이 있는 사람만 전체를 본다. 지점장은 자기 지점이니 전체를 보고, 마케팅 등은 가려 본다.
- C. 지금처럼 둔다(내부 직원만 쓰는 시스템).

### D2. 세션 만료·토큰 보관

- 만료: 12시간(지금) / 8시간(근무일) / 쓰지 않으면 1~2시간 뒤 만료(유휴 만료)
- 보관: `localStorage`(지금, XSS가 생기면 토큰이 빠져나간다) → httpOnly 쿠키 + CSRF 토큰(작업이 크다)
- 비밀번호를 바꾸거나 계정을 끄면 기존 토큰을 즉시 무효화할지. 계정에 `tokenVersion`을 두면 마이그레이션 1개로 된다. 지금도 계정을 끄면 최대 60초 안에는 막힌다(주체 캐시).

### D3. 실운영으로 넘어갈 때 데모 계정 정리

`render.yaml`은 지금 `DEMO_RESET=on`이고 데모 시드가 켜져 있다. 실고객을 넣기 전에:

1. `DEMO_RESET`·`DEMO_SEED`를 `off`로 바꾼다. 데모 목록은 그때부터 로그인 화면에서 저절로 사라진다(이번 수정).
2. 시드로 만든 140여 계정이 공개 비밀번호 `tongin1234!`를 쓴다. 다음 중 하나를 고른다.
   - A. 실운영 DB를 새로 시작하고(데모 계정 없음) 실제 직원 계정만 새로 만든다. (권장)
   - B. 그대로 쓰되, 실운영 모드에서 공개 기본 비밀번호로 로그인하는 것을 막는다. 이 경우 관리자 '비밀번호 재설정' 기능이 먼저 필요하다. 지금은 관리자가 남의 비밀번호를 다시 정하는 API가 없어, 막기만 하면 그 계정들이 영영 잠긴다. 그래서 이번에는 막지 않았다.
   - C. 첫 로그인 때 비밀번호 변경을 강제한다(`mustChangePassword` 열 추가).
3. `ADMIN_PASSWORD`를 강한 값으로 둔다. 운영에서 값이 없으면 admin을 만들지 않는다(이미 그렇게 되어 있다).

### D4. 접근(열람) 기록과 예전 감사 기록

- 지금은 **변경**(등록·수정·삭제)만 감사 기록에 남는다. 누가 어떤 고객을 열람했는지, 목록을 내보냈는지는 남지 않는다.
- 개인정보보호법 안전성 확보조치 기준은 개인정보처리시스템 접속기록(누가·언제·무엇을·어떤 처리)을 1년 이상 보관하고 월 1회 이상 점검하도록 한다(정보주체 5만 명 이상 등은 2년).
- 선택지:
  - A. 고객 상세·접수 상세·내보내기 버튼에만 열람 기록을 남긴다(가볍다). (권장)
  - B. 고객 데이터를 돌려주는 모든 GET을 기록한다(무겁다).
  - C. 지금처럼 둔다.
- 예전 감사 기록(이번 수정 전에 쌓인 `audit_log.after`)에는 고객 전화·서명 링크 등이 그대로 있다. 다음 중 하나를 고른다.
  - SQL로 `after`를 지운다(감사 기록의 행 자체는 남긴다).
  - 그대로 두고 감사 기록 조회 권한을 슈퍼관리자로만 줄인다.

### D5. 본사 권한 그룹 나누기

본사 직원 34명이 `HQ_STAFF` 한 그룹이다. 마케팅·디자인도 고객 삭제, 계약·입금 수정, 정산까지 할 수 있다.

- 권장 묶음: 영업·CS(고객·접수·견적·A/S) / 재무(입금·정산·청구) / 마케팅(캠페인, 고객은 보기만) / 일반(공지·결재·작업관리)
- 권한 그룹 화면에서 바로 나눌 수 있다(코드 수정 없음).

### D6. 외부 AI로 가는 개인정보

- AI 비서·에이전트가 고객 이름·전화·주소를 Anthropic API로 보낸다. 코드 실행 컨테이너를 쓰면 상대 쪽 샌드박스에 최대 30일 남을 수 있다.
- 선택지:
  - 에이전트 '개인정보 가리기' 가드레일을 기본으로 켠다(지금은 기본 꺼짐). 가리는 범위도 넓힌다. 지금은 휴대폰·이메일만 가리고 이름·주소·유선번호는 그대로다.
  - 대화·도구 기록·에이전트 실행 기록 보존 기한을 둔다(예: 90일 뒤 지움).
  - 개인정보 처리방침에 국외 이전(처리 위탁)을 고지·동의받는다(개인정보보호법 제28조의8).

### D7. 결재선을 어디까지 고치게 둘지

빈 결재선과 본인만 넣은 결재선은 막았다(H4). 다음 중 하나를 고른다.

- 양식 기본 결재선의 결재자는 빼지 못하고 더하기만 되게 한다.
- 지금처럼 누구든 결재자로 넣게 둔다.

### D8. 대시보드의 지점 순위·지역 매출

`GET /api/stats/overview`의 지점별·지역별 매출과 대시보드 '지점 순위'·'지점 지도'는 가맹점에도 모든 지점 수치를 보여 준다(개인정보는 아니다). 지점끼리 경쟁을 보여 주려는 의도인지 확인이 필요하다.

### D9. 비밀번호 규칙

지금은 6자 이상뿐이다. 권장은 8자 이상에 영문·숫자를 함께 쓰는 것이다. 이미 있는 비밀번호에는 적용하지 않고, 바꿀 때부터 적용한다.

### D10. 웹 전체 CSP

웹 앱 전체 CSP(스크립트 출처 제한)는 다음 외부 출처를 하나씩 허락해야 해서, 화면별로 확인한 뒤 넣는 게 안전하다.

- 다음 우편번호(daumcdn)
- 지도 타일
- 글꼴

먼저 `Content-Security-Policy-Report-Only`로 한 주 지켜보고 켜기를 권장한다. 지금 웹에는 `dangerouslySetInnerHTML`·`innerHTML`·`eval`이 없다. 사용자가 넣은 링크(업무분장 링크)는 서버가 `http(s)://`만 받는다.

  - 토스 웹훅: 비밀값으로 검증
- **단건 조회 IDOR**: id를 받는 GET 70개에 다른 지점 id를 넣어 봤다. 관리자는 13개 라우트에서 데이터를 받았고, 지점장은 **0건**이었다.
- **목록 응답**: 파라미터 없는 GET 116개 응답 어디에도 다른 지점 고객 전화번호가 없었다.
- **쓰기**: 접수·견적·계약·입금·작업·A/S·주문의 수정·상태 전이를 다른 지점 id로 부르면 403이었다.
- **AI 도구 실행**: 사용자 본인 토큰으로 내부 API를 부르므로 화면과 같은 권한·범위를 탄다. 업무 도구(고객·접수 검색, 문자)도 범위로 거른다. 외부 URL을 가져오는 도구는 없다(SSRF 없음). API 키는 서버 환경변수에만 있고 화면에는 '설정됨' 여부만 간다.
- **입력 검증**: 전역 `ValidationPipe`(`whitelist`·`forbidNonWhitelisted`·`transform`)를 쓴다. `$queryRaw`·`$executeRaw`는 모두 태그 템플릿(파라미터 바인딩)이고, `Prisma.raw`·`$queryRawUnsafe`는 없다.
- **문서 HTML**: 견적서·B2B 문서는 고객이 넣은 칸을 모두 이스케이프한다. 서명 그림은 PNG data URL 정규식으로 확인한다.
- **파일**:
  - 드라이브: 25MB 상한과 사용량 한도가 있고, 이름에서 경로·제어 문자를 걸러낸다. 내려받기는 `attachment`+`nosniff`다. 외부 공개 링크는 없고 직원끼리만 공유한다.
  - 근태 가져오기: `.xlsx`·`.csv`만, base64 15MB, 전용 권한(`ATTENDANCE.IMPORT`)이 필요하다.
  - AI 파일: `attachment`+`nosniff`.
- **오류 응답**: 500은 내용을 감추고 오류 번호만 준다(스택은 서버 로그에만).
- **비밀값 관리**:
  - `.env`는 커밋되지 않았고 `.env.example`만 있다.
  - 운영 `JWT_SECRET`은 Render가 만든다.
  - 웹 번들에 `VITE_` 비밀값이 없다(데모 비밀번호만 있었다 → M8).
- **비밀번호**: bcrypt(10). 운영에서 `ADMIN_PASSWORD`가 없으면 admin을 만들지 않는다.
- **권한 상승 방지**: 권한 그룹 바꾸기는 내 권한 안에서만 되고, 전체 범위는 전체 범위인 사람만 줄 수 있다. 마지막 슈퍼관리자는 보호된다.
- **퇴사 처리**: `POST /api/employees/:id/resign`이 계정을 끈다.
- **목록 상한**: 대부분 200건이고, CRM 2000건, 받은 알림 100건이다. 한 번에 전체 고객을 받는 API는 없다. 캠페인 받는 사람 고르기는 200건씩이지만 페이지 수에 상한이 없다. 범위 안 고객을 모두 훑을 수 있으므로 `MARKETING.READ`는 꼭 필요한 사람에게만 준다.
- **데스크톱 앱(Electron)**: 웹 주소를 여는 껍데기라 서버 쪽 수정이 그대로 적용된다.

## 배포 뒤 확인할 것

1. **견적서 보내기 → 고객 서명 링크 열기 → 서명.** 서명 링크 토큰은 이제 기본으로 읽지 않는 열이다. 보내기에서만 다시 읽는데, 로컬에서는 읽기 동작만 확인했고 발송 전체 흐름은 돌려 보지 않았다.
2. **견적서 화면의 '인쇄 · PDF 저장' 버튼.** 새 CSP에서 해시로 허락했다.
3. **대시보드 PDF 받기.** jspdf를 4.x로 올렸다.
4. **지점장 계정으로 확인할 것**:
   - 드라이브에서 회사 드라이브가 '보기'인지
   - 지점관리 현황에 자기 지점만 나오는지
   - 자재 발주 승인 버튼이 403인지(화면에서 버튼을 감추는 것은 후속)
